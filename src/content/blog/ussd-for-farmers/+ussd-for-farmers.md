Most of the farmers our platform serves will never open a web app. Some have no smartphone. Some have a phone but no data bundle that week. What almost all of them have is a basic phone and a short code they can dial.

That is why part of my work at Shamba Records is USSD: a plain-text, session-based menu that works on any phone, with no internet connection at all. This post is about the rules a USSD flow has to live inside, and what each one does to the design.

The farmer dials a code like `*123#`. The request goes through the mobile network to a gateway, and the gateway calls your server over HTTP with three things that matter: a session ID, the farmer's phone number, and `text`, which is everything the farmer has typed so far in this session, joined by `*`.

Your server answers with plain text, and the first word is the contract. `CON` means "show this screen and wait for an answer". `END` means "show this and close the session". Everything after that word is the screen.

Two facts shape everything else. The gateway sends the whole history, but only the last segment is new. And the phone remembers nothing between requests.

### Constraint 1: The screen is tiny

A single USSD message is limited to about 182 characters. You cannot show a table, you cannot scroll, and every extra word is a cost.

That forces good habits:

- **One question per screen.** If a screen needs two answers, it is two screens.
- **Short numbered options.** Typing `1` is easier than typing a word.
- **Always a way back.** Every screen offers `0` for back and `00` for home.

Keep the menus as data, not code. Ours live in a database tree, so changing a word or adding an option is an edit, not a deploy.

### Constraint 2: The phone keeps no state

So the server must. Each session is a row keyed by the gateway's session ID. It records who is dialling, whether they are logged in, and a breadcrumb stack of where they are in the menu. On every request you read only the newest input, load the session, move one step, save, and reply.

```js
// illustrative sketch, not production code
async function handle({ sessionId, phoneNumber, text }) {
	const input = text === '' ? '' : text.split('*').pop(); // only the newest answer
	const session = await sessions.findOrCreate(sessionId, phoneNumber);
	const screen = router.next(session, input); // walks the breadcrumb stack
	await sessions.save(session);
	return (screen.final ? 'END ' : 'CON ') + screen.text;
}
```

The breadcrumb stack is what makes `0` pop one level and `00` clear it, so a deep menu never leaves anyone lost.

### Constraint 3: Sessions die without warning

A tunnel, a weak signal, a network timeout. The session ends, and when the farmer dials again it is a brand-new session.

If you treat that as a stranger, they log in again and start from the top, in the middle of a registration or a loan application, on a screen where every step already costs effort. So when a new session starts, look for a recent one from the same phone number inside a window. We use 30 minutes. If there is one, carry over the login and the position, and ask before assuming: "Continue where you left off?"

Multi-step flows such as registration save each answer as it arrives, so "Continuing your registration…" lands on the exact question that was interrupted. The length of the window is a trade-off. Longer is kinder, but it matters more on a shared phone.

### Constraint 4: There is no login screen

There is no password field, so identity is the phone number plus a PIN. PINs are stored hashed, never in plain text. After a few wrong attempts the account locks for a while. Resetting a PIN needs a second factor: the National ID on file, then a one-time code sent by SMS.

New farmers can register through USSD itself. The account then waits for approval, and an SMS tells them when it is active.

### Constraint 5: The network will not wait

The gateway expects an answer within seconds. Anything slow cannot happen inside the request.

Deciding whether a farmer qualifies for a loan means many database queries. Doing that while the farmer waits would be too slow, so we run the scoring in a background job and cache the outcome for a couple of hours. The USSD reply only reads the cache.

Two rules keep that safe. The scoring job does not retry, because a stale result is worse than none: if it fails, the cache stays empty and the next dial queues it again. And a new score can only raise a farmer's limit, never lower it, so one bad run cannot take credit away.

There is also a boring fix that mattered. The first request of every session looks the farmer up by phone number. With no index on that column, and a `LIKE '%…'` pattern that cannot use one anyway, that lookup scanned the whole farmers table. Index the column, and match the exact number formats (`254…`, `0…`, `+254…`) so the index is actually used. It was the cheapest speed-up in the whole flow.

### Money rules stay on the server

The menu only displays. The rules live in the API behind it, the same API every channel uses: limits, an overall budget that caps how much can be committed, and approval steps. A farmer who is not eligible yet gets a screen that says when to try again, not a flat no.

### See what happened

When a farmer calls support, you want to replay their session. Log every turn with its input, the response and a timestamp. Log how long each step takes, so a slow screen shows up before the complaints do. And keep the gateway's end-of-session report (status, duration, cost) next to the session.

### What I would tell someone starting out

- Treat the 182 characters as a design brief, not a limit to fight.
- Keep the phone dumb and the server stateful.
- Assume every session will drop, and design resume first.
- Do slow work in the background. The reply is the one thing that cannot wait.
- Index the lookup you do on every first request.
- Log every turn.
